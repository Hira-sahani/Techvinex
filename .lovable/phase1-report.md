## 4. Migration compatibility report

42 migrations, chronological, all applied against `xfgyzcvrvgsntjenxecp`. Grouped
by portability class:

### 4.1 Safe (portable, apply as-is)  — 39/42
All `public`-schema tables, functions, triggers, GRANTs, RLS policies.
Every `CREATE TABLE` in `public` is followed by GRANTs and RLS policies — no
"invisible table" traps.

### 4.2 Storage-dependent  — 7 migrations
Files:
`20260405011153`, `20260509190334`, `20260509202726`, `20260608110310`,
`20260612093430`, `20260612121733`, `20260707054208`.

All touch `storage.buckets` and `storage.objects`. On a fresh target:

- `INSERT INTO storage.buckets` (line 1 of `20260405011153…sql`) creates the
  `blog-images` bucket. **Portable.**
- All `CREATE POLICY ... ON storage.objects` statements are portable — Supabase
  allows policies on `storage.objects` in every project.
- `UPDATE storage.buckets SET public = true` (`20260509202726` line 31) is
  portable but requires the bucket row to exist first — the file order handles
  that.

**Verdict:** portable. Nothing here depends on Cloud-specific state.

### 4.3 Extension-dependent  — 1 migration
File: `20260708115745_5c6ce125…sql`.

- `CREATE EXTENSION IF NOT EXISTS pg_cron WITH SCHEMA extensions;`
- `CREATE EXTENSION IF NOT EXISTS pg_net  WITH SCHEMA extensions;`
- `cron.schedule('cleanup-expired-buckets', '*/15 * * * *', …)` calls
  `public.cleanup_expired_rate_buckets()`.

**Portability risks on `yparkrguxoektihjpynr`:**

1. `pg_cron` and `pg_net` must be **enabled in the project's Extensions page**
   before this migration runs, or the `CREATE EXTENSION` will fail with
   `permission denied to create extension`. Supabase gates these behind a
   dashboard toggle; the SQL alone is insufficient on some plans.
2. `pg_cron` runs in the `postgres` database only, which is Supabase default —
   OK.
3. The cron entry will start firing **immediately** after apply. If the target
   is not yet the production DB, the job is harmless (`cleanup_expired_rate_buckets`
   only touches rows owned by this app), but be aware.

**Action:** in section 5, "owner actions", enable `pg_cron` + `pg_net` on the
target **before** `supabase db push`.

### 4.4 Conflicting  — 0
None of the migrations `DROP TABLE`, `TRUNCATE`, or otherwise assume prior
data. All were written idempotent-friendly (`DROP POLICY IF EXISTS` before
each recreation).

### 4.5 Destructive  — 0
No destructive statements. The only `DELETE FROM` statements live inside
`cleanup_expired_rate_buckets()` and scope by `expires_at < now()`.

### 4.6 Cloud-specific state  — 0
No migration references `supabase_functions.*`, `vault.*`, `net.http_*`, or
Lovable-injected roles/schemas. `auth.uid()` / `auth.users` references (143
occurrences across migrations) are standard Supabase — portable.

### 4.7 Ordering
The 42 files are timestamped and sort correctly. `supabase db push` will apply
them in filename order. No cross-file circular dependencies detected — the
storage-policy files each `DROP POLICY IF EXISTS` before recreating.

## 10. Limitations that persist after Phase 2

- Lovable preview URLs (`*.lovable.app`) will keep hitting Cloud
  (`xfgyzcvrvgsntjenxecp`) forever. Production on Vercel will not.
- Any Lovable Supabase tool call after cutover (`supabase--migration`,
  `supabase--deploy_edge_functions`, `supabase--storage_*`) still targets
  Cloud and creates drift. Treat Lovable as an editor only.
- `LOVABLE_API_KEY` is per-Cloud-project; the target needs its own value
  or the AI Gateway will 401 from the target's functions.
- Lovable-managed connectors (Google Search Console, ElevenLabs) are Cloud
  bindings — the target needs the raw provider keys copied in.
- Cloud stays attached to this project and remains billable. It is not
  disconnectable per Lovable's own docs.
